# Datpaq CLI Auth — Website Contract

This document specifies the website-side endpoints the **datpaq CLI** depends
on to perform browser-based OAuth login via Clerk. It lives in the CLI repo
(`github.com/datpaq/cli` → `docs/cli-auth-spec.md`) because the CLI is the
consumer of the contract; the website team implements against it.

## Overview

The CLI launches a one-shot local HTTP listener on a random port, opens the
user's browser to a page on datpaq.com that's gated by Clerk SSO, and waits for
the browser to be redirected back to localhost with a short-lived authorization
code. The CLI then exchanges the code for the user's API key.

```
┌────────┐  1. open browser   ┌─────────────────────────────┐
│  CLI   │ ─────────────────▶ │ datpaq.com/cli/auth         │
│ :PORT  │                    │ Clerk SSO + key selection   │
└────────┘                    └──────────────┬──────────────┘
    ▲                                       │
    │ 3. redirect to localhost              │ 2. POST /api/internal/
    │    /callback?code=...&state=...        │    cli/auth/select
    └───────────────────────────────────────┘    (Clerk session)
    │
    │ 4. POST /api/internal/cli/auth/exchange {code, state}
    │ 5. ← {api_key, user: {email, id}}
    ▼
 persist key to ~/.config/datpaq/config.toml
```

## Endpoint 1 — `GET /cli/auth`

**Purpose:** Browser-facing page that authenticates the user via Clerk, then
hands a one-time code back to the CLI's localhost listener.

**Query parameters:**

| Name    | Type   | Required | Description                                                                                  |
| ------- | ------ | -------- | -------------------------------------------------------------------------------------------- |
| `port`  | int    | yes      | Localhost port the CLI is listening on (e.g. `54321`). Validate range `[1024, 65535]`.       |
| `state` | string | yes      | Opaque nonce generated by the CLI. Treat as an opaque string; max length 128 chars.          |

**Behavior:**

1. If the user is not signed in to Clerk, redirect through the standard Clerk
   sign-in flow (google, github, email/password). Use the current page URL
   (including `port` and `state`) as the post-sign-in redirect target.
2. Once authenticated, show the user's active API keys and allow the user to
   select one or create a CLI key.
3. POST the selection, `port`, and `state` to
   `/api/internal/cli/auth/select`. The select route generates a one-time
   **authorization code** (≥128 bits of entropy, base64url) and stores it
   in Redis keyed by `code` with a 60-second TTL. The payload contains:
   - `datpaq_id`
   - `token_id` (the selected or newly created API key)
   - `state` (the value from the query string — must match on exchange)
   - `issued_at`
4. Redirect the browser to:
   ```
   http://localhost:{port}/callback?code={code}&state={state}
   ```

**Security notes:**

- The `port` parameter must be on `localhost` / `127.0.0.1` — never trust it for
  an absolute URL. Always render the redirect as `http://localhost:{port}/...`.
- The `state` parameter is opaque to the server; it's the CLI's CSRF defense.
- Reject `port` values outside the unprivileged range to prevent the page from
  being used as a generic redirector.

## Endpoint 2 — `POST /api/internal/cli/auth/select`

**Purpose:** Record the signed-in user's API-key selection and issue the
short-lived authorization code returned to the CLI through localhost.

**Auth on this endpoint:** Required. The request must use the logged-in Clerk
session established by `/cli/auth`.

**Request:** `Content-Type: application/json`

```json
{
  "port": 54321,
  "state": "n1G2k...opaque-nonce",
  "tokenId": "existing-token-id-or-null"
}
```

- `tokenId`: An active API key owned by the signed-in user, or `null` to create
  a new CLI key when the account is below its active-key limit.

**Response (200):**

```json
{ "code": "OBjFf...base64url" }
```

The browser then redirects to
`http://localhost:{port}/callback?code={code}&state={state}`.

## Endpoint 3 — `POST /api/internal/cli/auth/exchange`

**Purpose:** Exchange a one-time code for the user's persistent API key. Called
by the CLI from the localhost callback handler.

**Request:** `Content-Type: application/json`

```json
{
  "code": "OBjFf...base64url",
  "state": "n1G2k...opaque-nonce"
}
```

**Response (200):**

```json
{
  "api_key": "<api_key>",
  "user": {
    "id": "<clerk_user_id>",
    "email": "developer@example.com"
  },
  "expires_at": null
}
```

- `api_key`: The active API key chosen through the select endpoint, or the new
  CLI key created there.
- `expires_at`: ISO 8601 timestamp, or `null` if the key does not expire.

**Response (400)** — code expired, already consumed, or state mismatch:

```json
{ "error": "invalid_grant", "message": "Authorization code expired or already used." }
```

**Server-side logic:**

1. Atomically fetch and delete `code` from Redis (`GETDEL`).
2. Reject if it was not found or its 60-second TTL has elapsed.
3. Reject if `state` doesn't match the stored value.
4. Resolve the selected active key for the stored Datpaq user and return it.

Deleting on read makes every code single-use, including failed state-mismatch
attempts, and prevents replay if a response is observed in transit.

**Auth on this endpoint:** None. The endpoint must remain publicly reachable by
the CLI; the short-lived, single-use code plus matching state value is the
credential.

Both API handlers belong to Mainsite's `/api/internal/cli/auth` namespace. They
must not be placed under `/api/v1`, which is reserved by Nginx for ProAPI
gateway traffic and requires an API key before Mainsite can receive a request.

## Implementation notes

Design choices the website implementation should align with:

1. **API key returned:** the user's primary key, or one labeled `cli` when
   the user has multiple keys. Implementation may default to either; the
   CLI doesn't depend on the label.
2. **Dashboard visibility:** keys returned via this flow should be
   discoverable in the user's dashboard (recommended label: "Created by
   CLI") so users can rotate them out-of-band.
3. **Rotation:** out of scope for v1. A future `datpaq auth rotate`
   command can be added once the endpoint exists.
4. **CORS:** not required — the localhost callback is a same-browser
   server-side redirect, not an XHR.

## CLI implementation

The CLI consumer of this contract lives in `internal/cli/auth_login.go`.
It:

- Start `http.Server` on a random free port (`net.Listen("tcp", "127.0.0.1:0")`)
- Open `https://datpaq.com/cli/auth?port={port}&state={nonce}` via the OS
  default browser
- Wait up to 5 minutes for the `/callback` request
- Validate state, POST to `/api/internal/cli/auth/exchange`, persist the key via
  `cfg.SaveCredential(api_key)`
- Show "✓ Logged in as {email}" and return

Fallback paths preserved from the generated scaffold:
- `datpaq auth set-token <key>` — paste from dashboard
- `DATPAQ_API_KEY=...` env var — CI / scripted usage
